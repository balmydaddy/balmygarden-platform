# 영수증 앱 화면 기준 (RECEIPT-UI-01)

> 수립: 2026-08-28, CEO 지시 ("hotdeal.zip 벤치마킹해서 UI를 바꾸겠다, 기준만 수립해달라")
> 벤치마킹 대상: `hotdeal.zip` 상품 상세 화면 (2026-08-28 CEO 제공 스크린샷 실측)
> 담당: ARIA(A-01) / 관련 기준: PLAT-01(화면 증설 금지), NOTION-01(결론 우선), COST-01

---

## 0. 결론 먼저

**hotdeal.zip이 우리보다 기능이 많은 게 아니라 방향이 반대다.**

hotdeal은 **살 것**을 다룬다 — 지금 시장에 나온 가격을 모아 보여준다.
영수증 앱은 **산 것**을 다룬다 — 내가 이미 낸 돈을 기록한다.

가격 비교를 그대로 붙이면 우리는 남이 잘하는 걸 늦게 따라가는 앱이 되고, 정작 우리만
가진 자산(실제 지불가 이력)은 화면에 안 나온다. **그러니 베낄 것은 기능 목록이 아니라
화면 문법이다.** 아래 1절이 가져올 것, 2절이 가져오면 안 되는 것이다.

---

## 1. hotdeal.zip에서 가져올 것 — 화면 문법 4가지

### 1-1. 한 화면에 큰 숫자는 하나만

상세 화면에서 `2,729,000원`이 압도적으로 크고 나머지는 전부 보조 정보다. 눈이 어디를
봐야 하는지가 0.5초 만에 정해진다.

영수증 앱의 대응물은 **"이번 달 얼마 썼나"** 하나다. 그 숫자 하나가 화면에서 제일 크고,
카테고리·매장·건수는 그 아래 보조다. 지금처럼 목록이 먼저 나오면 사용자가 매번 합계를
머리로 계산해야 한다.

### 1-2. 숫자 옆에 그 숫자의 조건을 적는다 (가장 크게 얻을 항목)

이게 hotdeal의 진짜 기능이다. 가격 비교표의 `비고` 칼럼을 보면 같은 상품인데 판매처마다
**가격의 정의가 다르다**는 걸 숨기지 않고 밝힌다.

| 판매처 | 표시 가격 | 비고에 적힌 조건 |
|---|---|---|
| 네이버 | 2,729,000원 | 핫딜모음에서 제공한 가격 |
| 11번가 | 2,572,410원 | 검색 확인 가격, 배송비 별도일 수 있음 |
| 롯데하이마트 | 2,771,100원 | 기본 판매가 기준, 최대혜택가 2,543,390원 |
| (하단) | 2,237,660원 | 최저가 기준, 배송비 3,000원 별도 |

숫자만 보면 롯데하이마트가 제일 비싸 보이는데, 비고를 읽으면 최대혜택가 기준으로는 제일
싸다. **비고가 없으면 표가 사용자를 속이는 셈이 된다.**

영수증 앱에서 이 자리에 들어가야 하는 것은 **OCR이 이 숫자를 얼마나 믿고 있는지**다.

| 우리 쪽 대응 항목 | 비고에 적을 것 |
|---|---|
| 인식된 금액 | 자동 인식 / 사용자가 고친 값 / 인식 실패로 직접 입력 |
| 상품명 | 원문 그대로 / 이름 보정됨(`NameCorrectionModal` 경유) |
| 카테고리 | 자동 분류(14종 규칙) / 사용자 지정 |
| 합계 | 영수증 합계와 항목 합이 일치 / 불일치(차액 표시) |

마지막 줄이 특히 중요하다. 항목 합과 영수증 합계가 안 맞으면 **안 맞는다고 화면에 쓴다.**
조용히 한쪽 값을 쓰면 그 순간부터 기록 전체를 못 믿게 된다.

### 1-3. 출처와 시각을 항상 붙이고, 원본으로 돌아갈 길을 남긴다

hotdeal은 제목 바로 아래에 `오늘 08:44` · `출처 아카라이브` · `원본글` 링크를 붙인다.
가격이 이상하면 사용자가 직접 원본을 확인할 수 있다.

영수증 앱의 대응물은 **찍은 시각 · 매장명 · 원본 영수증 이미지 보기**다. 숫자가 이상할 때
원본 사진으로 한 번에 돌아갈 수 없으면 사용자는 앱을 못 믿는다. OCR 앱에서 이건 편의
기능이 아니라 신뢰의 최소 조건이다.

### 1-4. 탭은 3개를 넘기지 않는다

hotdeal 상세는 `가격 비교` / `가격 흐름` / `상품 분석` 셋이다. 넷째가 없다.

우리도 셋을 넘기지 않는다. PLAT-01이 이미 정한 원칙이다 — **카테고리·탭·섹션을 임의로
늘리지 않는다.** 벤치마킹이 탭 증설의 명분이 되면 안 된다. 새 탭이 필요하면 기존 탭
하나를 없앨 수 있는지 먼저 검토한다.

## 2. 가져오면 안 되는 것

### 2-1. 가격 비교 기능 자체

붙이려면 판매처별 크롤링이나 상용 가격 API가 필요하다. 둘 다 비용이 붙고(COST-01), 붙인
다음에는 판매처가 화면을 바꿀 때마다 깨진다. 유지보수가 계속 드는 기능인데 **우리 강점이
아니다.**

우리가 가진 건 "내가 실제로 낸 값"이고, 그건 크롤링으로는 못 얻는 데이터다. 자원을 여기
쓴다.

### 2-2. 구매하기 CTA와 제휴 링크

hotdeal에는 `구매하기` 버튼이 화면 상단에 크게 있다. 그 앱은 사게 하는 앱이라 맞는 배치다.

영수증 앱은 **쓴 돈을 보러 오는 앱**이다. 여기에 구매 버튼을 붙이면 앱의 목적과 정면으로
충돌한다. 지출을 줄이려고 켰는데 사라고 권하는 화면이 된다. 제휴 수익이 필요하면 그건
별도 판단 사항이고, 최소한 지출 요약 화면에는 두지 않는다.

### 2-3. 남의 시세를 우리 데이터인 것처럼 섞는 것

hotdeal조차 `핫딜모음에서 제공한 가격`과 `검색 확인 가격`을 구분해 적는다. 우리가 외부
시세를 들여온다면 내 영수증 데이터와 **같은 표에 같은 서식으로 놓지 않는다.** 섞이는
순간 어느 게 내가 낸 돈인지 알 수 없게 된다.

## 3. 우리만 가진 것 — 여기에 투자한다

hotdeal이 못 하는 것들이다. 화면 개편의 중심은 이쪽이어야 한다.

| 자산 | hotdeal | 우리 |
|---|---|---|
| 지금 파는 값 | 있음 | 없음 |
| **내가 실제로 낸 값** | **없음** | **있음** |
| **같은 상품을 다시 샀을 때의 내 가격 추이** | 없음 | 있음 |
| **매장별로 내가 실제 낸 값의 차이** | 없음 | 있음 |
| 카테고리 분류 | 상품 카테고리 | 지출 카테고리 14종 (이미 구현됨) |

hotdeal의 `가격 흐름` 탭에 대응하는 우리 버전은 **"내 구매가 추이"**다. 남의 시세 그래프가
아니라 내가 같은 우유를 언제 얼마에 샀는지의 기록이다. 데이터가 남의 것이 아니라 내
것이라는 점에서 이건 베끼는 게 아니라 우리 쪽이 원본이다.

## 4. 화면 규칙 (개편 시 적용)

1. **결론 우선.** 화면 최상단은 목록이 아니라 답이다 — 이번 달 지출 한 줄.
2. **숫자에는 조건을 붙인다.** 자동 인식인지, 사람이 고친 값인지, 합계가 맞는지 (1-2).
3. **원본으로 가는 길을 항상 남긴다.** 어느 화면에서든 원본 영수증 이미지로 한 번에 (1-3).
4. **탭 3개 상한.** 늘리려면 하나를 없앤다 (1-4, PLAT-01).
5. **색은 3단계로만.** 🔴 사용자 확인 필요 / 🟡 자동 보정됨 / 🟢 확정. NOTION-01의 색 규칙을
   화면에 그대로 옮긴다.
6. **빈 상태를 설계한다.** 영수증 0장일 때 화면이 무엇을 말하는지 정해둔다. 대부분의 사용자가
   처음 보는 화면이 이것이다.
7. **틀렸을 때를 먼저 설계한다.** OCR은 틀린다. 틀린 값을 고치는 경로가 몇 번 탭인지가
   이 앱의 실질 품질이다.

## 6. 하지 않기로 한 것

- **hotdeal의 기능을 항목별로 대응시키지 않는다.** 도메인이 반대라 1:1 대응은 성립하지 않는다.
- **UI 시안을 지금 그리지 않는다.** 적용할 코드 위치가 미확인이라 그린 시안이 맞을지 알 수 없다.
- **가격 비교·최저가 기능을 로드맵에 넣지 않는다.** 비용과 유지보수가 붙는데 우리 강점이 아니다
  (2-1). 필요해지면 그때 CEO 결정 사항으로 다시 올린다.
